# Техническое задание (ТЗ)

## AI-конструктор коммерческих предложений (КП) для сервисной компании

**Версия документа:** 1.0
**Статус:** draft
**Основание:** `AGENTS.md` (спецификация продукта и правила разработки)

---

## 1. Общие сведения

### 1.1. Проблема

Подготовка коммерческого предложения в сервисной компании занимает у менеджера от 1 до 3 часов: нужно собрать информацию о задаче клиента, подобрать услуги, вписать цены, выстроить структуру и оформить документ. Ошибки в ценах и устаревшие формулировки приводят к потерям сделок и переделкам.

### 1.2. Решение

Веб-приложение, в котором менеджер заполняет короткий бриф, ИИ-модель (GigaChat / YandexGPT) генерирует черновик КП по утверждённому шаблону структуры, менеджер проверяет и правит текст, после чего документ выгружается в PDF.

### 1.3. Цель проекта

Сократить время подготовки КП с часов до минут при сохранении контроля качества: цены всегда из прайса, текст проверяет человек, PDF идентичен отредактированной версии.

### 1.4. Термины

| Термин | Определение |
|---|---|
| Бриф | Форма с данными о клиенте, задаче, услугах, сроках и бюджете |
| КП | Коммерческое предложение — итоговый документ для клиента |
| Шаблон КП | Утверждённый список разделов КП с инструкциями для ИИ |
| Прайс | Справочник услуг с ценами, ведёт руководитель |
| Guard | Слой проверки ответа модели (цены, галлюцинации, ПДн) |
| Менеджер / Руководитель | Роли пользователей (см. `AGENTS.md`) |

---

## 2. Назначение и пользователи

### 2.1. Назначение

Продукт для внутреннего использования сервисной компанией. Результат работы — черновик КП по брифу, который человек проверяет и выгружает в PDF.

### 2.2. Роли

| Роль | Возможности |
|---|---|
| **Менеджер** | Заполняет бриф, запускает генерацию, редактирует черновик, просматривает предпросмотр, скачивает PDF, работает с историей КП |
| **Руководитель** | Всё, что доступно менеджеру, плюс: редактирует шаблон структуны КП и прайс услуг |

Реализация ролей в MVP — переключатель роли в интерфейсе (без системы аутентификации). Элементы управления шаблоном и прайсом отображаются/активны только для роли «Руководитель».

## 3. Функциональные требования

### 3.1. Экран «Бриф»

**FR-1. Форма брифа.** Форма содержит поля:

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| Клиент | текст | да | Название компании клиента |
| Задача | многострочный текст | да | Описание задачи/проблемы клиента |
| Услуги | мультивыбор из прайса | да (≥1) | Выбор из справочника услуг |
| Сроки | текст | да | Например: «2 недели», «до 30.06» |
| Бюджет | текст/число | нет | Если пусто — в КП не выводится сумма |

**FR-2. Валидация.** При нажатии «Сгенерировать КП» приложение проверяет обязательные поля; при ошибке — список неверных полей, введённые данные сохраняются. Вызов ИИ при ошибках невозможен.

**FR-3. Цены услуг.** Для каждой выбранной услуги подставляется цена из прайса. Если у активной услуги цена не заполнена — в брифе отображается пометка «цена уточняется».

### 3.2. Экран «Черновик с редактором»

**FR-4. Генерация.** По валидному брифу модель генерирует текст КП по разделам активного шаблона. Порядок разделов — как в шаблоне. Показывается индикатор загрузки; при ошибке API — сообщение и возможность повторить без потери брифа.

**FR-5. Структура ответа.** Ответ модели парсится на разделы (заголовок + текст). Нераспознанный ответ — ошибка с предложением повторить.

**FR-6. Редактирование.** Каждый раздел доступен для правки в текстовом редакторе (Streamlit `text_area` или подобном). Правки сохраняются в КП как новая версия.

**FR-7. Повторная генерация.** Кнопка перегенерации всего КП или отдельного раздела с сохранением текущего текста в истории версий.

**FR-8. Ценообразование (критично).** Итоговые цены в тексте КП формируются **только кодом** из прайса. Модель не генерирует и не изменяет суммы. Отсутствующая цена → текст «цена уточняется».

### 3.3. Экран «Предпросмотр и PDF»

**FR-9. Предпросмотр.** Отображение КП в том виде, в каком оно уйдёт в PDF (разделы, цены, реквизиты-заглушки).

**FR-10. Экспорт PDF.** Кнопка «Скачать PDF» формирует файл через reportlab. Текст PDF **дословно совпадает** с отредактированной версией (допускаются только переносы строк при верстке). Кириллица отображается корректно (TTF-шрифт, см. `AGENTS.md`).

**FR-11. Имя файла.** `КП_{клиент}_{YYYY-MM-DD}_v{версия}.pdf`.

### 3.4. Экран «История КП»

**FR-12. Список.** Таблица сохранённых КП: клиент, дата, версия, статус (черновик/финал).

**FR-13. Открытие.** Из истории КП открывается на редактирование/просмотр с сохранением текста, версии и даты.

**FR-14. Версионирование.** Каждое сохранение после правок создаёт/обновляет версию КП (v1, v2, …) с датой; прежние версии остаются в истории.

### 3.5. Экран «Настройки» (Руководитель)

**FR-15. Шаблон КП.** Редактирование списка разделов: заголовок + инструкция для модели + порядок + активность. Изменения применяются к следующим генерациям.

**FR-16. Прайс услуг.** CRUD-справочник: название, цена, единица (опционально), активна. Удаление — мягкая деактивация (чтобы старые КП оставались валидными).

## 5. ИИ-составляющая

### 5.1. Провайдеры

- **GigaChat API** (Сбера) — основной вариант.
- **YandexGPT / Yandex AI Studio** — альтернатива.

Провайдер выбирается в конфигурации (переменная окружения `AI_PROVIDER`), оба реализуют общий интерфейс `src/ai/base.py`. Захардкоженных URL/ключей в коде нет.

### 5.2. Промпт

- Системная инструкция: роль — автор коммерческих предложений сервисной компании; писать по разделам шаблона; **категорически запрещено выдумывать цены и реквизиты**; при отсутствии данных использовать «цена уточняется» / «уточняется отдельно».
- В запрос передаются: текст брифа, активный шаблон (разделы + инструкции), актуальные цены выбранных услуг из прайса.
- Формат ответа модели: строгая структура по разделам (например, маркеры `## Заголовок`), парсится кодом.

### 5.3. Guard-слой (`src/ai/guard.py`)

1. **Проверка цен.** После генерации кодом из текста извлекаются все числа-суммы (₽, руб., цены). Каждое сверяется с прайсом/брифом: число отсутствует в допустимом наборе → заменить на корректное значение из прайса или «цена уточняется» + запись в лог. *Тест-кейс критерия готовности: модель не выдумывает цены.*
2. **Обезличивание.** Перед отправкой промпта в модель и перед записью в лог ПДн (телефоны, email, ФИО контактов) обезличиваются или исключаются.
3. **Парсинг.** Невалидный ответ модели → понятная ошибка и повтор, бриф не теряется.

### 5.4. Логирование

- Каждый вызов: timestamp, провайдер/модель, промпт (после обезличивания), ответ, длительность, ошибки.
- Хранение: локальный файл/таблица, ретеншн ≤ 30 дней.
- Ключи API в логи и UI не выводятся.

### 5.5. Безопасность ключей

- `GIGACHAT_API_KEY` / `YANDEX_API_KEY` — только переменные окружения или `.env`.
- `.env` в `.gitignore`; в репозитории только `.env.example` с плейсхолдерами.
- Хардкод ключей — блокер на ревью.

## 6. Модель данных

```
briefs        (id, client, task, deadline, budget, created_at)
brief_services(brief_id, service_id)                 -- выбранные услуги
proposals     (id, brief_id, version, status, sections_json, created_at)
              -- sections_json: [{header, body}, ...]
services      (id, name, price, unit, active)
templates     (id, name, sections_json, active)      -- sections_json: [{header, instruction}, ...]
ai_logs       (id, ts, provider, model, prompt, response, duration_ms, error)
```

Все таблицы создаются автоматически при старте (`src/storage.py`), при пустой БД — сид: активный шаблон по умолчанию и пример прайса.

## 8. Сценарий приёма (happy path)

1. Менеджер открывает приложение → страница «Бриф».
2. Заполняет клиента, задачу, выбирает 3 услуги из прайса, указывает сроки; бюджет пуст.
3. Нажимает «Сгенерировать» → валидация проходит → вызов GigaChat → разделы по шаблону.
4. Переходит на «Черновик», правит формулировки → версия сохраняется.
5. На «Предпросмотре» видит: цены из прайса, у одной услуги «цена уточняется» (цены в прайсе не было) — выдуманных сумм нет.
6. Скачивает PDF → текст совпадает с отредактированным, кириллица корректна.
7. На «Истории» видит КП: клиент, дата, v2.
8. Руководитель открывает «Настройки», меняет прайс и разделы шаблона → применяется к следующей генерации.

## 9. Критерии готовности (acceptance)

| # | Критерий | Проверка |
|---|---|---|
| A1 | PDF дословно совпадает с отредактированной версией (кроме переносов строк) | Тест `test_pdf.py` + ручная сверка |
| A2 | Модель не выдумывает цены: нет сумм вне прайса/брифа | Тест `test_price_guard.py` (мок ответа с галлюцинацией) |
| A3 | Цена отсутствует → «цена уточняется», а не число | Тест guard + сценарий 8.5 |
| A4 | API-ключ только в окружении, `.env` не в репозитории | Ревью + `.gitignore` |
| A5 | Валидация обязательных полей до вызова ИИ | Тест `test_validation.py` + ручной прогон |
| A6 | История КП: сохранение и открытие с версией и датой | Ручной прогон сценария |
| A7 | Шаблон и прайс редактируются только ролью «Руководитель» | Ручная проверка переключения роли |
| A8 | Кириллица в PDF корректна | Открытие файла |
| A9 | Логи промптов/ответов без персональных данных | Тест guard + осмотр логов |
| A10 | Повторная генерация/правки не теряют бриф | Ручной прогон |

## 10. Этапы реализации

| Этап | Содержимое | Результат |
|---|---|---|
| 1 | Каркас: структура, storage.py, сиды, requirements, .env.example | Приложение запускается, таблицы создаются |

## 11. Риски

| Риск | Влияние | Митигация |
|---|---|---|
| Модель выдумывает цены | Критично — неверное КП | Guard-слой (5.3), тест A2, запрет в промпте |
| Медленный/недоступный API ИИ | Задержка генерации | Таймаут 60 с, повтор без потери брифа, понятная ошибка |
| Кириллица ломается в PDF | Непригодный документ | Обязательный TTF-шрифт + тест A8 |
| Утечка ключа | Безопасность | Только окружение, `.env` не коммитится (A4) |
| ПДн в логах/промптах | Несоответствие требованиям | Обезличивание в guard (A9) |
| Нестандартный ответ модели | Слом парсинга | Строгий формат + ретрай + ошибка без потери данных |
